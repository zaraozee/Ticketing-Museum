feat(payments): tambah pemeriksa konfigurasi Midtrans dan tutup celah UAT

Dua acceptance criteria Fase 9 (AC-4 pembayaran produksi, AC-6 UAT museum
pilot) terblokir hal di luar kendali pengembang: akun Midtrans produksi,
domain HTTPS tetap, dan seorang perwakilan museum. Commit ini mengerjakan
seluruh bagian yang masih dapat dikerjakan tanpa akses itu, tanpa mengklaim
AC mana pun selesai.

1. payments:check-midtrans (AC-4)

Perintah diagnostik baru, padanan auth:check-google untuk pembayaran. Menangkap
kesalahan konfigurasi yang gejalanya menyesatkan sebelum uang sungguhan dipakai:

- prefix kunci tidak cocok dengan mode (SB-Mid- pada MIDTRANS_IS_PRODUCTION=true,
  atau kunci produksi pada mode sandbox);
- MIDTRANS_SNAP_URL tertinggal di host sandbox meski mode produksi menyala;
- Signature Secret Key belum dipisahkan dari Server Key;
- APP_URL localhost atau bukan HTTPS pada mode produksi (webhook tidak akan
  pernah sampai, tiket tidak pernah terbit);
- konfigurasi sedang di-cache sehingga .env baru diabaikan.

Opsi --probe mengirim GET /v2/{order}/status untuk order yang tidak ada. Tidak
membuat transaksi. Jawaban "Transaction doesn't exist" berarti kunci DITERIMA;
401 berarti ditolak. Dijalankan pada konfigurasi nyata proyek ini: exit 0,
kunci diterima Midtrans (HTTP 200), tanpa membuat transaksi apa pun.

Dikunci 12 tes. Dua tes penjaga (prefix kunci, localhost produksi) dibuktikan
"menggigit" dengan sengaja merusak kodenya lebih dulu: masing-masing membuat
tes gagal, lalu kode dikembalikan.

2. Matriks ketertelusuran UAT (AC-6)

UAT_PLAN.md 4A memetakan seluruh 34 skenario ke tes otomatis yang sudah ada,
sehingga sesi dengan museum pilot hanya memakai waktunya untuk hal yang tidak
dapat dibuktikan mesin: tampilan, kamera gate, popup Snap, email nyata, dan
pembayaran produksi. Setiap rujukan nama tes diverifikasi cocok dengan suite.

3. Bug #12: HTTP 500 pada ekspor laporan pengelola

Pemetaan di atas menemukan dua skenario tanpa jaring pengaman sama sekali (C4
ekspor laporan, D1/D2 antrean anomali admin). Menulis tesnya langsung
memunculkan bug nyata: /organizer/reports/export memakai $profile->id tanpa
null-check, sedangkan halaman laporannya sendiri sudah menangani pengelola
tanpa profil organisasi dengan paginator kosong. Akibatnya kasus yang sah itu
berakhir sebagai HTTP 500, bukan 404.

Diperbaiki dengan $profile?->id. Dikunci 11 tes di
AnomalyAndExportRegressionTest, termasuk isi CSV (angka harus sama dengan
transaksi), kepemilikan museum pada ekspor, antrean anomali yang tetap kosong
untuk transaksi wajar, dan resolve anomali.
